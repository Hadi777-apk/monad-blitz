## 2. 为什么适合 Monad Blitz

- 原创可演示应用：围绕有限资源、双贡献赛道和透明分配，而不是照搬代币模板。
- Monad 的实际用途：游戏币与奖励账本部署在测试网，多玩家能提交领奖交易并查询结果。
- 体验目标：短轮次反馈、多玩家状态同步、领取结果可查；低延迟优势需要实际测量，不能拿官方网络峰值当本游戏实测。
- 比赛目标是原型，不在一天内承诺生产级反作弊、无信任数据证明或完整经济生态。
- 所有应用与合约代码在活动正式时间段内开始开发。当前提交只包含赛前方案文档。

## 3. 必做范围

1. 一张可用矿场页面：连接钱包、正确网络提示、明确开始与停止计算。
2. 可验证计算挑战：钱包/轮次绑定，答案验算、截止处理与去重。
3. 按轮积分、排名、状态和明确的预计/已结算奖励区分。
4. 固定总量代币与奖励分配：两池预算冻结，先让 A 的 8 枚轮分配完整跑通。
5. 玩家能领取已结算余额，页面显示实际交易结果与可查询链接。
6. 公开规则、每轮积分/分配明细、裁判限制、公开 GitHub 和稳定访问链接。
7. 交易失败、重复领取、错网络和空轮等关键边界有可解释的处理。

如果只完成 A，必须明确展示「B 实验模式尚未开放；200 枚保留在独立预算中」，不能把 A 的 800 枚说成可争夺全部 1000 枚。

## 4. 优先级较低的选做范围

- B 模式：先核对一个工具的统计结构，完成基线、增量、缓存口径、重复同步检查，再进行本地读取接入。
- 若 B 来不及接入，只展示规则和关闭状态；如用模拟数据演示，放在单独明确标识的模拟实例，不声称真实读取。
- 基础矿工动画、首次领奖成就、全场灯塔和矿工外观。
- 一键查看历史轮次和个人历史。

首版不做：交易市场、支付充值、收费加速、额外 AI 调用、主网发行、提现换 MON、跨游戏资产互通、团队矿池、移动 App、多模型全面适配。

## 5. 三人协作建议

| 角色 | 主要责任 | 与其他人约定的交接物 |
| --- | --- | --- |
| 前端/体验 | 矿场、钱包、状态、排名、领取与规则页 | 按赛道区分积分，交易成功后以链上结果更新 |
| 合约/结算 | 固定供应、双池预算、轮次唯一性、分配与领取 | 实例标识、只读状态、可领取余额和错误语义 |
| 服务/验证 | 挑战签发验算、时间窗、去重、积分归集；有余力再接 B | 每轮唯一钱包积分列表、请求回执、公开结算明细 |

人少时按流程合并责任，不改变结算公式。团队人数遵守本场活动最多 3 人要求；表格只是分工建议，没有替队友认领任务。

## 6. 关键交接约定

- 每条贡献必须有游戏实例、钱包、赛道、轮次和唯一记录身份，避免跨实例重放。
- 模式 A 的「已提交」「已接受」「已拒绝」分开，前端哈希速度不等于有效积分。
- 模式 B 的累计快照与增量不能混用；同一记录只能确认一次。
- 前端使用链上已结算金额作为确定奖励，服务端预测只能显示为预计。
- 金额传递用整数最小单位，展示时才格式化小数；舍入规则不能由各端自行选择。
- 提交链上前冻结本轮最终积分和分配明细；交易重试沿用同一轮与同一结果。
- 正式开始前选定裁判、规则版本、网络、实例和测试名单。钱包和统计来源的真实数据不写进仓库。

## 7. 后续实现验收清单

这些是将来需要执行的验收场景，本轮没有执行游戏测试。

| 场景 | 预期结果 |
| --- | --- |
| 初始发行 | 总量恰为 1000；团队未预留，奖励合约持有全部初始分配量 |
| 比例算例 | A 60/30/10 得 4.8/2.4/0.8；B 1/3 得 0.5/1.5 |
| 总量边界 | 每池有效轮不超过 100；A≤800、B≤200、合计≤1000 |
| 舍入 | 8 枚分给 3 个等积分钱包，最小单位分配后恰好分完 |
| 无参与者 | 空轮不消耗该池有效轮和预算，下一有效轮不叠加空轮额度 |
| 只开 A | B 始终保留 200，不能被 A 或管理员提走 |
| 重复挑战/轮次 | 同一答案只记一次；同一轮不能重复链上结算 |
| 错误/过期绑定 | 错钱包、错实例、错轮、过期或截止后收到的挑战不计分 |
| 实验用量 | 首次基线无奖励，断线重连不重复累计；650+800 得 1 分余 450 |
| 故障恢复 | 验证延迟明显展示，链上交易失败能重试且不重算/重复发放 |
| 领取 | 拒签与手续费不足保留余额；重复请求不重复付款；收款人为对应钱包 |
| 最后一轮 | 第 100 个有效轮按固定额度分配，之后该赛道不再发新奖励 |
| 权限 | 裁判不能改额度/收款地址或撤回奖励，管理员不能提走奖池；明确仍信任裁判积分 |
| 隐私 | 上传内容无代码、提示词、密钥、文件路径和原始日志 |
| 资金账本 | 累计领取 + 待领取 + 未分配预算 = 1000，玩家转账不重置额度 |
| 旧标签页更新 | 入口/版本检查不缓存，资源有内容哈希，失效分块可恢复；旧页面能切换到新构建 |

此外需要在预定演示设备和测试网测量挑战难度、轮次反馈、30 人结算批次和手续费表现，当前没有结果。

## 8. 五分钟现场演示

| 时间 | 展示内容 |
| --- | --- |
| 0:00–0:35 | 一句话说明：1000 枚固定游戏宝石，按贡献争夺；明确 BLITZ/MON 区别 |
| 0:35–1:30 | 两个钱包开始计算，出现有效答案，展示不同积分与预计份额 |
| 1:30–2:20 | 60 秒演示轮结束，验证后展示公开积分与实际分配 |
| 2:20–3:20 | 一个玩家领取，展示链上成功和余额；解释未领取部分仍留在账本 |
| 3:20–4:15 | 展示 B 实验设计；真实接入成功才演示读取，否则明确为未开放 |
| 4:15–5:00 | 总量守恒、实验池隔离、裁判限制、公开仓库与后续路线 |

演示应让两个浏览器/钱包并行贡献。不要把快速切换的钱包伪装成很多真实玩家，也不要在失败时把未完成交易口头说成成功。

## 9. 项目价值与后续方向

短期验证：有限资源竞争是否能让开发者参与一个完整的链上游戏循环，玩家是否愿意回来参与下一轮。

商业方向假设：未来可向开发者活动提供有品牌外观的互动游戏服务，按活动服务收费；先验证体验与部署可靠性，不把代币升值或交易手续费当作收入依据。当前没有客户、定价或商业验证数据。

只有在能拿到更可信用量证明后，再讨论把 B 从自报实验升级为可靠贡献赛道。真实跨游戏成绩也需要游戏服务方签发可验证结果，不能任意读取别人游戏数据后直接信任。

## 10. 队友优先讨论的三个问题

1. 是否接受「1000 BLITZ，800 计算 / 200 实验用量」作为首版默认？这只是设计，尚未发行。

3. 谁负责前端、合约、验证服务，测试名单和演示设备由谁准备？

其他参数已有默认方案，无需在实现前无限扩展。等用户明确开始开发后，按活动规则和当时确认的方案实施。
