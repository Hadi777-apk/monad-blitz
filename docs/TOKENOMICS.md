# BLITZ：总量与分配规则 v0.2

日期：2026-10-17。状态：方案，未实现、未发行。v0.2 替代 v0.1 的中心裁判积分与最大余数排序方案；1000 枚总量、800/200 双池及按贡献分配的目标保持不变。

## 1. 固定总量与资金隔离

| 项目 | 规则 |
| --- | --- |
| 游戏币 | 暂定 BLITZ，ERC-20，18 位小数 |
| 总量 | 单个游戏实例 1000 × 10^18 个最小单位，一次性进入奖励金库 |
| 团队预留、增发、转账税、销毁 | 首版均不提供；无管理员抽取奖励或升级增发入口 |
| A：计算挑战 | 800 枚，100 个有效轮，每轮 8 枚 |
| B：AI 用量实验 | 200 枚，100 个有效轮，每轮 2 枚；真实性证据不足时保持关闭 |
| 交易资金 | 独立交易托管合约中的买家货款、卖家押金，不来自游戏奖池 |
| 交易支付资产 | 由订单指定，不强制 BLITZ；首版限定单一测试支付资产 |
| MON | 网络手续费；测试交易使用什么资产必须另外明确标注，不承诺奖励 MON |

外部转入奖励金库的资产不增加游戏预算，玩家转回 BLITZ 也不重置已分配额度。1000 枚是这个实例的总量，不是整个 Monad 上所有同名代币的总量。

## 2. 轮次、预算预留与关闭

- 标准轮长 300 秒，实例冻结 T0，以 `[T0+r×300, T0+(r+1)×300)` 定义第 r 个全局时间窗口。
- 独立演示实例可以启动前选择 60 秒；不能运行中改规则、重开相同实例预算。
- 每轮可以由任何人发起开启，无需后台批准；迟开不延长该轮结束时间。
- 每个赛道本轮第一次有效贡献被合约接受时，预留一次该池轮奖励，并消耗一个有效轮名额。
- 没有有效贡献的空轮不预留奖励、不消耗名额；不把空轮额度堆到下轮，也不挪用另一赛道预算。
- 同一赛道最多预留 100 个有效轮；第 100 轮已开启的贡献仍可持续到该轮截止，之后不能预留第 101 轮。
- 截止以贡献交易被区块链纳入时的合约时间判断；本地完成、请求已送达后台、交易仍在待打包队列中，均不代表计入上一轮。
- 轮次结束后，任何人可调用关闭轮次，冻结总积分。关闭只处理该轮状态，不遍历参与者，不要求后台签名。
- 不要求前一轮先被人工关闭，预算在第一笔有效贡献时已锁定，避免延迟关闭导致超分配。
- 没有参与者或 B 未开放时，不承诺固定日期把 1000 枚全部发完；剩余预算不得由管理员提走。

两赛道持续活跃时，100 轮贡献窗口共 500 分钟，约 8 小时 20 分钟；交易确认与领取另计。

## 3. A 的有效贡献

挑战信息来自合约公开状态：链 ID、实例地址、规则版本、轮次、轮次种子、参与钱包、nonce、固定难度 d。

合约执行 SHA-256 条件检查、钱包/轮次绑定、截止和重复答案检查。只有有效且上链的答案才产生贡献记录与积分，任何后台都不能直接提交一个任意积分数字。

每个有效答案贡献 `w=2^d`。同一实例先固定难度，初值 d=16 仅是待设备与手续费实测的设计建议。以后若要变难度，应启动新规则版本/实例，不能改已开启的轮次。

轮次种子在开启时由合约绑定前一区块哈希和实例/轮次域，避免提前准备完整未来答案；不是可证明无偏随机源，区块生产者和开启时机仍可能影响它。不把此种子用于随机分配有价值奖品。

第三方可以转发答案，但收益地址已绑定原钱包；转发或复制不能把奖励改到转发者名下。没有新人补贴、按钱包封顶或按钱包保底；不承诺完全防女巫或抵抗专业硬件优势。

## 4. B 的计分与限制

- 口径仍为非缓存输入 tokens + 输出 tokens；累计 1000 个有效 tokens 为 1 分，零头向该钱包下一轮结转。
- 首次接入建基线，不计算历史总量；累计快照、会话切换和缓存字段必须先完成来源映射，无法正确处理的来源不接入。
- 本地日志、截图、用户签名与哈希都不证明模型服务真的消耗了用量。
- 主要测试实例默认关闭 B 的奖励接入，保留 200 枚预算；不能把 B 伪装成已去中心化。
- 若另建自报实验实例，须在实例启动前固定可信证明提交方、其权限和版本，页面明确标示。它可以造假或拒绝提供证明，这个限制不会被多签或打包哈希自动消除。
- 实验实例的证明必须绑定钱包、轮次、唯一记录、截止与累计来源，合约拒绝重复记录；积分真实性仍依赖固定提交方。
- 没有可靠数据来源时，只在独立模拟界面展示流程，不给主要实例提交伪造积分；B 的限制不能通过影响 A 的积分或预算绕过。

650+800 个有效 tokens 对应 1 分余 450；不要求为了游戏额外购买或消耗 AI 额度。

## 5. 分配公式：贡献区间累计差额

这一条是 v0.2 的舍入变更。最大余数法要求知道并排序所有玩家，不适合无界参与人数；新方法每条贡献可独立计算，保留完整预算和整数精度。

对本轮依次被接受的贡献：

- S 是该贡献被接受前本轮累计积分，w 是本条贡献的积分。
- 合约给本条贡献记录不可重叠区间 `[S,S+w)`，并把总积分增加 w。
- 关闭轮次后 T 为最终总积分，B 为本轮奖励的整数最小单位。
- 本条贡献奖励 = `floor(B×(S+w)/T) − floor(B×S/T)`。
- 每个钱包的奖励为自己所有贡献区间奖励之和；每个区间只能领取一次。

所有贡献区间连续覆盖 `[0,T)`，累加后恰好是 `floor(B×T/T)−floor(0)=B`。整数运算使用可处理乘除精度与溢出的实现，不能用浮点数。

每条贡献的金额与精确比例之差小于一个最小单位；一个钱包累计误差上限随其区间数量增长。链上顺序可能影响极微小舍入差额，但不会增加本轮总预算。展示时的小数四舍五入不等于实际链上金额。

为保持边界清晰，首版每条有效答案形成一条记录；批量只是在有界交易中验证多条原始答案，不能让服务端任意合并、重排或增添工作量。

## 7. 领取、故障与可用性

- 玩家凭贡献编号直接向合约领取，收款人固定为记录中的钱包；别人代触发也不能改收款人。
- 单笔只处理有界数量的记录，可分批领取。无需平台数据库提供一份秘密证明，也不遍历全场玩家。
- 无人为领取过期时间；未领取的奖励不会重新分配。网站/排名服务停机不取消链上权益。
- 轮次未关闭时，用户可自己关闭再领取；奖励只在成功确认后算到账。
- 失败交易不产生已领取标记；成功领取后重复提交不再发币。
- 交易未在截止前被纳入，不能事后由后台补记。首页必须区分「本地找到」「待确认」「链上接受」「已领取」。
- 首版链上核心规则不可升级，不能新增管理员冻结既有领取的权限。缺陷可能无法在原实例修复，这是不可变设计的明确取舍。

## 8. 资金守恒：把开放轮的预算也算进去

定义：

- R：尚未被任何有效轮预留的预算。
- E：已预留给开放/尚未关闭轮次的预算。
- D：已关闭轮次承诺的累计奖励。
- C：实际累计领取，满足 `0≤C≤D`。
- U：已关闭轮次尚未领取的奖励，`U=D−C`。

始终满足：`R+E+D=1000`，等价于 `R+E+U+C=1000`。

每池单独核对，A≤800、B≤200。B 关闭时其 200 枚仍在 R。所有有效轮结束并关闭后 E=0；只有两池均完成 100 个有效轮，才有 R=0、D=1000。C 可以更小，差额仍属于 U。

资金记录的是协议预算与发放责任，不会因为玩家转回代币、外部误转或当前钱包余额变化而重置。
